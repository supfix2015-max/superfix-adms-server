# Original Att2000_V4 on SQL Server — direct read-only access

No SQL Server-to-MySQL data conversion is required.

The **original** `Att2000_V4` SQL Server 2025 database stays untouched on Hostinger, with its tables `Employee`, `Attendance`, `Device`, and `EmployeeTemplate`. New ADMS device uploads and all control-plane tables **continue to use MySQL**, while the admin can browse the original historical records directly over the Docker `coolify` network. There is no bi-directional sync in this release.

## What was implemented

- Microsoft ODBC Driver 18, PHP `pdo_sqlsrv`, `sqlsrv` in the application's Dockerfile.
- Independent `legacy_sqlsrv` connection using a `SELECT`-only SQL login.
- An opt-in, admin-only `/admin/legacy` page, with four tabs:
  - Employees: `Employee.Id`, `BadgeNumber`, `NAME`, `DepartmentId`, `CardNo`, `HiredDay`
  - Attendance: `Attendance.Id`, `BadgeNumber`, `VerifyTime`, `VerifyType`, `Status`, `DeviceSerialNumber`, with date and badge/device filters
  - Devices: serial, alias, model, historical status, IP, push protocol. **Historical registrations are not proof the devices are online.**
  - Template metadata: fingerprint template type/index/version/format only; **never fetches or displays the binary `Template` column**
- Links from existing dashboard, Employees, Attendance, and Devices screens, shown only when the feature is enabled.
- No SQL Server migrations, writes, imports, fingerprint replay, or device command dispatches in these routes.
- Existing ADMS `/iclock` endpoints and MySQL models remain unchanged.

## Test deployment configuration

Deploy the draft branch to a **separate non-public test environment** before merging. The original app/database must keep running.

Use Coolify environment variables (never commit secrets):

```dotenv
APP_ENV=staging
DB_CONNECTION=mysql
# Keep existing operational MySQL DB_HOST, DB_DATABASE, DB_USERNAME, DB_PASSWORD
LEGACY_SQLSRV_HOST=superfix-attendance-sql
LEGACY_SQLSRV_PORT=1433
LEGACY_SQLSRV_DATABASE=Att2000_V4
LEGACY_SQLSRV_USERNAME=adms_legacy_reader
LEGACY_SQLSRV_PASSWORD=<enter-in-Coolify-secrets>
LEGACY_SQLSRV_ENCRYPT=yes
LEGACY_SQLSRV_TRUST_SERVER_CERTIFICATE=false
LEGACY_SQLSRV_BROWSER_ENABLED=true
```

Both the SQL Server container and the test Laravel container must be attached to the `coolify` Docker network. SQL Server should **not** expose TCP/1433 publicly.

**TLS:** ODBC Driver 18 verifies certificates by default. The correct production solution is a trusted server certificate matching the container's DNS name. The earlier `LEGACY_SQLSRV_TRUST_SERVER_CERTIFICATE=true` workaround was only for short internal tests; do not use that insecure bypass for production. Keep `LEGACY_SQLSRV_BROWSER_ENABLED=false` until TLS and access controls are verified.

**Staging background worker:** When `APP_ENV=staging` or `testing`, the container entrypoint now disables Supervisor's `queue:work database` worker, so copied old MySQL jobs cannot execute. Keep `ADMS_PILOT_ENABLED=false` to deny all device ingress, and do not assign this test application an endpoint used by any physical terminal.

**Web access:** Do not publish employee data over Coolify's autogenerated HTTP `sslip.io` URL without HTTPS and access restrictions. Prefer an internal-only or IP-restricted test endpoint. Laravel admin authentication is still required.

**Database user:** `adms_legacy_reader` is granted SELECT privileges only on the four legacy tables. Avoid `sa` in Laravel; do not enable write permissions.

## First live ADMS device pilot (2026-11-11)

Direct SQL Server attendance write plumbing is now implemented behind **off by default** gates. This does not change the original database schema.

**Before enabling it:**
1. Run `php artisan adms:legacy-write-readiness --serial=BZD5261200843` from the deployed Laravel test container. Examine actual SQL Server required `Attendance` columns, historical Status/VerifyType values, and existing history for the pilot serial. Fix mappings if the report flags any non-null/non-default column or unexpected values.
2. Verify an off-server SQL Server backup/restoration plan and that the original `Att2000_V4` database stays ONLINE.
3. Establish a new SQL Server login (not `sa` or the read-only account), with only `SELECT, INSERT` on `dbo.Attendance`; do not grant UPDATE, DELETE, db_owner, or permissions to biometric tables. The writer uses `sp_getapplock` in a transaction for serial/time/badge/status deduplication. Test with real device punches and retries. Confirm that the permissions allow a transaction-scoped application lock.
4. Require `LEGACY_SQLSRV_ATTENDANCE_TIMEZONE=Asia/Dubai` if the original SQL Server timestamps represent UAE device-local time. Validate against the prior record timestamps before going live.
5. Enable only **one** explicit pilot serial on the device endpoint `at1.superfix.ae` (HTTP only if device model does not support HTTPS), with the admin interface on `https://at2.superfix.ae`. Prevent anonymous admin/password access on the HTTP device endpoint. Do not assume serial numbers alone authenticate a terminal. Keep token verification or other network controls when supported.

The optional cutover config is:

```dotenv
# Remain FALSE until the above readiness checks/backup are complete.
LEGACY_SQLSRV_ATTENDANCE_WRITE_ENABLED=false
LEGACY_SQLSRV_ATTENDANCE_WRITE_SERIALS=BZD5261200843
LEGACY_SQLSRV_ATTENDANCE_TIMEZONE=Asia/Dubai
LEGACY_SQLSRV_WRITE_USERNAME=<new-limited-writer-login>
LEGACY_SQLSRV_WRITE_PASSWORD=<secret>
LEGACY_SQLSRV_WRITE_TRUST_SERVER_CERTIFICATE=false
ZKTECO_DISPATCH_COMMANDS=false
ZKTECO_AUTO_PULL_EMPLOYEES_ON_CONTACT=false
ADMS_PILOT_ENABLED=false
ADMS_PILOT_SERIALS=BZD5261200843
ZKTECO_AUTO_REGISTER_DEVICES=false
```

After an approved one-device pilot, set `LEGACY_SQLSRV_ATTENDANCE_WRITE_ENABLED=true` and `ADMS_PILOT_ENABLED=true` only for the serial listed above. On receiving ATTLOG: the application **first** attempts a direct INSERT into original SQL Server Attendance using transaction lock plus existing-record lookup; if successful it also records its existing MySQL operational log, then returns OK to the terminal. Failure returns an error so the device can retry; idempotency checks prevent duplicate historical records. MySQL remains necessary for admin authentication, devices, callback logs, and command metadata.

**Important:** Until a production write pilot is verified, the HTTP device endpoint must remain pilot-disabled. `ZKTECO_DISPATCH_COMMANDS=false` prevents sending queued commands through `/iclock/getrequest`, even if the MySQL staging copy has pending commands. The staging queue worker also remains off. Never turn on bulk user/fingerprint replays during this phase.

The 22 rows in the legacy `Device` table are historic registrations, not confirmation of 22 connected devices. Verify physical serials and polling one by one, and do not attempt mass cutover or re-enrollment until the pilot and full template compatibility validation succeed.

## 2026-11-11 write readiness result

Read-only `adms:legacy-write-readiness --serial=BZD5261200843` succeeded against the deployed `Att2000_V4`: the only non-nullable field in `dbo.Attendance` is identity `Id`, and `InsertDate` has a SQL default. Historical values include `Check-In`, `Check-Out`, `Overtime-In`, `Overtime-Out` and `FingerPrint`, `Password`, plus literal verification `2`. Historical device/punch rows for the UA300 test serial are both zero.

The updated `LegacyAttendanceValueMapper` uses raw ZKTeco ATTLOG status 0/1/2/3/4/5 to preserve individual directions (especially overtime-in/out); ambiguous/unsupported status values now fail closed rather than inventing a generic `Overtime` value. Raw verification code `2` is preserved as found in the historical database. Run `php artisan test --filter=LegacyAttendanceValueMapperTest` on the new test build prior to enabling writes.

After creating the limited writer login, run this **read-only** permission audit in the test container:

```bash
php artisan adms:legacy-write-readiness --serial=BZD5261200843 --check-writer
```

Only a writer with SELECT+INSERT on `dbo.Attendance`, without UPDATE/DELETE or template access, is accepted. This checks permissions but does not actually INSERT. A separate write pilot, inspected on both original SQL Server and MySQL, must be tested with an actual UA300 punch before any wider rollout.
